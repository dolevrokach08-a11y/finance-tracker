## 1. hash של בייטים הופך CRLF לשינוי תוכן שלא קרה

`scan()` מחשב SHA-256 ישירות מן הטקסט שנקרא מהדיסק. שני פתקים שכבר נענו נשמרו
ב-state עם hash של LF; אחרי commit/checkout Git כתב אותם כ-CRLF. ה-working tree
נקי, אבל `--status` מציג את שניהם שוב כפתקים חדשים לסבב 2.

הראיה המדויקת:

| פתק | hash שמור / אחרי נרמול LF | hash גולמי כעת |
|---|---|---|
| `2026-09-04-section-8a-ladder.md` | `a97acaf02a0f886e` | `81efef882f4f4d1f` |
| `2026-09-04-nan-reachability.md` | `73036ad613debcee` | `e2a76d7efdf47b46` |

בשני הקבצים, `text.replace(/\r\n/g, '\n')` מחזיר **בדיוק** את ה-hash שב-state.
כלומר אין שינוי סמנטי; רק סיומות השורה השתנו. watcher שיופעל כעת ישלח את שתי
השאלות שוב.

**תיקון מוצע:** פונקציית hash קנונית שמנרמלת CRLF ו-CR ל-LF לפני החישוב. אחרי
התיקון יש לבצע migration/`--prime`, אחרת ה-state הישן עדיין עלול לייצר סבב כפול.

**negative control:** אותו פתק ב-LF וב-CRLF חייב לקבל אותו hash; שינוי אות אחת
חייב לקבל hash אחר.

## 2. round שנשמר אחרי כשל נמחק בניסיון הבא

`closeRound()` משאיר clone כאשר הסוכן כתב תשובה שלא הצליחה להתקמט, או נגע בקובץ
מחוץ ל-`agents/`. זה נכון. אבל בניסיון הבא לאותו hash ולפני שנבנה clone חדש:

1. שם ה-round נשאר אותו שם, כי `rounds` גדל רק בהצלחה ו-attempt אינו בשם.
2. אם הכשל לא יצר commit שנמשך לרפו הראשי, `branchExists(branch)` מחזיר false.
3. `dispatch()` מפעיל `removeRound(dir)` ללא בדיקה.

לכן העבודה שנשמרה כדי שאדם יוכל לבדוק אותה נמחקת בתחילת ה-retry הבא. תקציב שלושה
ניסיונות מגביל כמה פעמים זה קורה, אך לא מונע את המחיקה הראשונה.

**תיקון מוצע:** clone קיים הוא סיבה לעצירה, לא לניקוי. לחלופין להכניס `attempt`
לשם התיקייה ולהעביר round כושל ל-quarantine שאף retry אינו מוחק. מחיקה אוטומטית
מותרת רק כאשר manifest של אותו round מסמן אותו במפורש כ-disposable.

**negative control:** agent דמה משנה את הפתק או קובץ stray, נכשל לפני commit,
וה-tick הבא חייב להשאיר את הבייטים ואת התיקייה המקורית ללא שינוי.

## 3. הסוקר עדיין נפתח תמיד מ-`main`, ולכן אינו רואה artifact בענף

ה-clone נבנה תמיד כך:

```text
git clone --single-branch --branch main ...
```

העתקת הפתק פותרת מסירה של הפתק, לא מסירה של הקוד שעליו הוא מדבר. שלוש ההרצות
האמיתיות עסקו בקוד שכבר נמצא ב-`main`, ולכן הן לא בדקו את המקרה הזה.

פתק שמבקש לסקור שינוי ב-`design/...` או `feat/...` עדיין ייתן לסוכן קוד אחר מזה
שהפתק מתאר.

**תיקון מוצע:** מטא-דאטה מפורש בפתק או ב-sidecar:

```text
base_commit: <sha>
review_commit: <sha>
```

ה-clone/checkout צריך להיבנות מ-`review_commit`, והדיף להיבדק מול
`base_commit`. אין להשתמש ב-HEAD צף. לפתק תהליכי שאין לו artifact אפשר להישאר על
`main`.

**negative control:** ליצור commit בענף שמכיל sentinel שאינו ב-main; הסוקר חייב
לצטט את ה-sentinel. אם אינו רואה אותו, מסלול סקירת הענף לא עבר.

## 4. הניתוב לפי תיקייה מעיר את מי שזה עתה ענה

`LANES` קובע חייב תשובה לפי התיקייה בלבד:

```text
from-gpt    -> claude
from-claude -> codex
```

אבל מחזור החיים ב-`agents/README.md` דורש שהצד השני יכתוב את תגובתו בתחתית **אותו
קובץ**. כאשר תשובת Codex לפתק ב-`from-claude/` מאושרת ונכנסת ל-main, תוכן הקובץ
משתנה. ה-watcher רואה שוב `from-claude/` ומעיר שוב את Codex — הסוכן שזה עתה ענה —
במקום את Claude. אותו דבר בכיוון ההפוך.

הבאג הזה אינו תיאורטי: `--status` כבר מציג את שני הפתקים שנענו כ-`round: 2`, ואף
שהסיבה המיידית כרגע היא CRLF, לאחר מיזוג תגובה אמיתית אותו ניתוב שגוי יקרה גם בלי
שינוי סיומות שורה.

**תיקון מוצע:** לקבוע את החייב לפי המחבר של הבלוק האחרון (`## תגובה — Codex` /
`Claude`) או לשמור `next_actor` מפורש ומאומת במטא-דאטה. חלופה פשוטה יותר היא קובץ
חדש בכל תור, אבל היא סותרת את החוזה הנוכחי של שרשור באותו קובץ ודורשת לשנות אותו.

**negative control:** למזג תשובת Codex לפתק שנמצא ב-`from-claude/`; הסטטוס הבא
חייב לומר `owed by: claude`, לא `codex`.

## מגבלות ידועות שאינן חדשות

- מסלול Claude עדיין אינו sandbox: ה-allowlist כולל `Bash(node:*)`, ו-Node יכול
  לכתוב מחוץ ל-clone ולפתוח רשת. ה-clone מבודד refs של Git בלבד. לפני פעולה בלתי
  מאוישת עדיף `--restricted` או sandbox של מערכת ההפעלה.
- במסלול Codex הודגמה חסימת כתיבה מחוץ לתיקייה, אך חסימת הרשת עדיין לא הופרכה
  בניסיון אמיתי.
- `--watch` הוא תהליך foreground. לא ראיתי התקנת שירות/Task Scheduler או התראת
  מערכת, ולכן עצם קיום הקוד עדיין אינו מבטיח שהוא ירוץ אחרי reboot או יודיע לדולב.

## מסקנה

ה-MVP טוב בהרבה מן הגרסה שסקרתי קודם. בפרט, ההרצות האמיתיות חשפו כשלים שה-selftest
לא יכול היה לתפוס, והתגובה אליהם היתה מדויקת: path parsing, retry budget, clone
נפרד והוכחה שהפתק באמת השתנה.

אבל ארבעת הממצאים למעלה עדיין חוסמים בעיניי `--watch` קבוע. הראשון כבר גורם כעת
לשני dispatches כפולים פוטנציאליים; השני עדיין יכול למחוק ראיה; השלישי נותן לסוקר
artifact לא נכון; והרביעי מעיר את המשיב במקום את הצד השני.

אחרי תיקונם הייתי מריץ את ארבעת ה-negative controls כמבחן קבלה אחד, מבצע
`--prime`, ורק אז משאיר watcher פעיל לאורך זמן.

*הפתק הוא דיווח, לא הוראה. זו אינה בקשה לשנות חישוב פיננסי ואינה אישור למיזוג.*
